Account Risk Platform

A multi-tenant system that ranks each CSM's accounts by renewal risk using a fitted model, runs on its own whenever new data lands, and lets a CSM trace every number back to the data behind it. The pipeline is deterministic, and an LLM does one narrow, checked job inside it: reviewing flagged accounts.

Built with Airflow, DuckDB, dbt, LightGBM, Claude Opus 5.5 and Streamlit, on 3 years of synthetic data for 4 tenants.

The warehouse is the single source of truth. The agent reads it through tools bound to one account and writes only to its own outbox; it never fetches from source systems, never changes a score, and never sends a customer email. The dashboard reads a snapshot published after each agent run, so it can't block or corrupt the pipeline.

Edge cases anticipated

Data arrival

  • A ticket from three weeks ago arrives today. It lands as a new file and bronze loads it once (file manifest). Silver rebuilds and the last 13 weeks are rescored, but each score only uses rows the warehouse had received by its as-of date, so past scores reproduce exactly.
  • Webhook retries deliver the same event twice. Staging keeps the first copy to arrive per source ID: 1,226 retried product events are removed.
  • Event names changed over three years. A mapping seed translates old names (report_created → report.create), and the old and new export keys are read as one column.
  • A feed stops silently. ops.source_freshness scores every feed per tenant, and the dashboard shows a banner on every page. Quarry's stalled Stripe feed reads 600 hours behind.
  • Timestamps in mixed timezones. Everything is stored in UTC; Gmail's RFC 2822 headers are parsed with their offsets; the warehouse session is pinned to UTC. Next step Tenant-local "Monday" for a digest.

Account identity

  • Stripe customer with no Salesforce ID. Matched by contact email or company domain. Each rule's confidence is measured on 1,260 labeled matches; records with no confident match (51 Stripe customers) go to quarantine. An email shared by two accounts (a consultant, a shared mailbox) matches neither, rather than the first one found.
  • Shared domains like gmail.com. Excluded from domain matching through a seed list, or every personal mailbox would merge into one "account".
  • Several workspaces, parent and child accounts, mergers. Merged Salesforce duplicates redirect to their master; each workspace maps to its account; parent and child stay separate accounts. Next step Roll-up to the parent.
  • The same real company is a customer of two tenants. Never merged: matching runs inside a tenant only. 31 such pairs stay apart, and a test enforces it.

Modeling

  • Accounts with almost no data. They get an "insufficient data" status, separate from low risk, and the dashboard says so. They're still scored, and dark accounts near renewal go to the agent.
  • Features that leak the outcome. Customer notices (cancellation requests, scheduled cancellations, agent risk flags) aren't model inputs; they're shown to the CSM as known risk. Accounts that already gave notice are left out of training and evaluation: they are nearly all positives and would inflate every metric. Features only use data known by the as-of date, and the rolling time windows have 90-day purge gaps.
  • Accounts younger than 90 days. A new-customer flag and tenure are inputs, so the model learns their pattern. Next step A separate onboarding cohort model.
  • Churn or downsell is only about 2% per 90 days. Judged on PR-AUC and the precision of each CSM's top 10, not accuracy, which a model can hit by predicting "renews" for everyone.
  • High ticket volume is ambiguous. Engaged customers file tickets too. Inputs use urgent and incident tickets, bad CSAT and resolution time, not raw counts; noisy-but-loyal accounts are a trap group in the evaluation.
  • A CSM saves a flagged account. Save plays are kept out of the model, because they react to risk already seen. Next step Feed interventions back as labels.

Agent and automation

  • An account flips between yellow and red every week. Hysteresis: red needs two weekly runs at 0.25 or above and holds until it drops below 0.18; yellow enters at 0.10 and exits below 0.07.
  • The account already has an open escalation or is mid-negotiation. The agent can route it to "suppress" only if that evidence exists. The CSM still gets the brief as a note, without a duplicate task.
  • Ticket text says "ignore previous instructions". Customer text is tagged as untrusted, and the tools are read-only and bound to the case. Tested: a planted "route to no_action" was ignored, and the brief flagged it.
  • An agent run crashes halfway. Cases are keyed on tenant, account and score date, and actions are de-duplicated, so a rerun skips handled accounts. Results commit at the end, so a crash repeats the batch's model calls.
  • A CSM has 25 red accounts, or no assigned owner. At most 3 per CSM and 12 per run are reviewed; the rest wait for the next run. Unowned accounts go to the team lead.
  • The risk is a failed payment. Routed to billing, which requires a failed charge in the evidence. A CSM call doesn't fix a card decline.

Tenancy

  • A tenant has few accounts and little churn history. It uses the pooled model and the pooled calibration curve; a tenant gets its own curve only with 50+ positives in the calibration half of validation (none today).
  • One tenant's 3-year backfill. Each tenant's first sync carries its pre-window history; all warehouse writes share one pool, so loads queue rather than collide. Next step Per-tenant quotas.
  • A tenant leaves. Next step Delete its partitions and agent records, then retrain the pooled model without its rows.

Traceability

  • The brief says "usage down 40%"; the feature says 38%. The validator rejects it: every number in a sentence must appear in a fact the sentence cites. Numbers are compared as values, so "3" doesn't pass because a fact says "30", and dates and evidence IDs aren't mistaken for numbers. One retry, then the rules write a template brief.
  • The model was retrained since last week. Training is monthly and separate from scoring. A promoted model rescores all 14 weekly dates at once, so week-on-week change always compares one model with itself. Every score row carries its model version, and ml.model_registry records every model, the time windows it used and every promotion decision.
  • A CSM disputes a score. The dashboard goes from score to reasons to the exact input row, and from each brief sentence to its evidence, its source rows and the landed bronze file.

Details handled without being asked

  • Some churners are undetectable on purpose.The generator includes churn with no warning signs (budget cuts, acquisitions), so evaluation reflects the real ceiling instead of a perfect score.
  • "Unknown" is different from "healthy".Accounts with thin data say "insufficient data" on screen, and stale feeds get a banner.
  • Calibrated probabilities.Platt calibration, fit on validation accounts that the booster's early stopping didn't see. Accurate at the low end, where most accounts sit (0.4% predicted, 0.4% observed); it over-predicts the 10–35% range, which a larger calibration set will tighten. Isotonic was tried and dropped: on about 100 positives it overfit into steps whose ties cost ranking quality.
  • Priority weighs money and time.Risk × ARR × up to 2× inside 180 days of renewal, so a yellow account renewing soon can outrank a red one renewing in 11 months.
  • A gate for promoting new models.A retrained model goes live only if it beats the rules baseline and doesn't lose to production on the same test window. The windows roll forward with the labels, so each monthly retrain learns from one more month and is tested on data no earlier model trained on. Every decision is logged.
  • Labels come from what the business recorded.Churn and downsell come from Salesforce and Stripe, never from the generator's answers; they match all 639 real churns. Future CSM feedback as extra labels.
  • Gmail privacy.Metadata only: no message bodies are generated or stored. Next step PII redaction and per-tenant opt-in before ticket text reaches the LLM.
  • LLM cost control.Triage caps (12 per run, 3 per CSM), prompt caching, medium effort: about $0.05 per account, logged per run in agent.runs.
  • Missing renewal dates.The contract anniversary stands in, and "renewal date missing" is a model input rather than a silent default.
  • Monitoring the monitor.Feed freshness per tenant, quarantine counts and dbt tests on every build. Next step Feature drift between training and scoring.
  • Secrets stay out of the image.The API key is injected at runtime from a git-ignored .env; without it the agent runs on rules.
  • One writer, by design.Every warehouse task shares a single-slot pool, so DuckDB's one-writer rule never surfaces as a random failure. On-demand agent reviews go through Airflow and queue for the same pool; ad-hoc queries go to the published snapshot, because any session on the live file, read-only included, blocks the pipeline's writes.
